1. Propósito y alcance

Este manual explica cómo importar y ejecutar en Postman la colección de pruebas de la API de Mostrador, un sistema multi-tenant para comercios que ofrece catálogo, autopedido con código QR, órdenes y pantallas de contenido. La colección reproduce, en orden, los 12 archivos .http de backend/http y comprueba automáticamente el código de estado de cada solicitud y algunos campos clave de la respuesta.

Alcance: la API del backend en un entorno de desarrollo local (http://localhost:3000). Quedan fuera la publicación en un espacio de trabajo en la nube de Postman, las pruebas de carga y la aplicación móvil o web que consume la API.

Todos los ejemplos de respuesta provienen de una ejecución real de la colección contra el backend local el 2 de noviembre de 2026. Los tokens se muestran abreviados.

2. Requisitos previos

  • Postman de escritorio (o Postman CLI 1.x, o Node.js con npx newman).
  • PostgreSQL local con una base de datos para el proyecto y el archivo backend/.env apuntando a ella (el modelo está en backend/.env.example).
  • Node.js y las dependencias del backend instaladas: npm ci dentro de backend.
  • ffprobe (FFmpeg) disponible para el backend, porque mide la duración de los videos que se suben en 10 Content.
  • El backend en ejecución en el puerto 3000.

2.1 Base de datos

Desde la carpeta backend:

npm run db:apply
# opcional: datos de demostración (local1 y local2), idempotente
psql -h localhost -U postgres -d <base> -f ../database/seeds/dev_local1.sql

npm run db:apply aplica los scripts SQL de database/scripts (el esquema). La colección no necesita el seed: crea su propio tenant, dueño, local y datos en la carpeta 01 Admin. El seed de mobile/README.md solo es necesario para la demostración de la aplicación.

2.2 Backend

npm run start:dev

Comprobación rápida: abrir http://localhost:3000 en el navegador; una respuesta 404 en formato JSON indica que el servidor escucha (no existe una ruta raíz).

3. Importar la colección y el entorno

  1. Abrir Postman y elegir Import (esquina superior izquierda).
  2. Arrastrar los dos archivos de backend/postman: Mostrador.postman_collection.json y Mostrador-local.postman_environment.json. También sirve Files y seleccionarlos.
  3. Confirmar con Import. Aparecen la colección «Mostrador API» (con 12 carpetas) y el entorno «Mostrador local».
  4. En el selector de entorno de la esquina superior derecha, elegir Mostrador local.

3.1 Directorio de trabajo para los archivos de prueba

Las solicitudes que suben archivos (imagen de producto, contenido de pantalla) referencian los archivos de backend/http/samples con rutas relativas a backend/postman, por ejemplo ../http/samples/promo.png. Postman necesita saber contra qué carpeta resolverlas:

  1. Abrir Settings, pestaña General.
  2. En Working directory, elegir la carpeta backend/postman del repositorio.
  3. Si Postman marca un archivo como no encontrado en el cuerpo form-data de una solicitud, volver a seleccionarlo con Select files desde backend/http/samples.

Los archivos usados son promo.png (imagen válida), promo.mp4 (video corto válido), largo.mp4 (video de más de 60 s) y no-soportado.txt (texto, para probar el rechazo por formato).

5. Autenticación y roles

El backend usa tokens JWT. El flujo es:

  1. POST /auth/login con email y contraseña devuelve { "access_token": "eyJ..." }.
  2. La colección guarda el token en adminToken o ownerToken y cada solicitud autenticada lo envía como Authorization: Bearer (pestaña Authorization de la solicitud).
  3. El token vence a los 10 minutos (el backend fijó 600 segundos en las pruebas). Por eso cada carpeta comienza con su propio login.
RolQuién esVariable de tokenAlcance
rootAdministrador de la plataformaadminTokenContexto admin (X-Tenant-Slug: admin): /me y /tenants. También puede operar dentro de cualquier tenant.
ownerDueño de un tenantownerTokenBackoffice del tenant: locales, categorías, productos, contenido, pantallas y órdenes. No administra tenants.
Sin autenticaciónCliente público y televisor(ninguna)/public/*, /media/* y /player/:token/playlist (el televisor se identifica con el token de la pantalla).

Ejemplo real de login (token abreviado):

POST /auth/login


{
  "email": "dueno-xxxxxxxx@local3.test",
  "password": "Dueno-dev-2026!"
}

200 OK

{
  "access_token": "eyJ..."
}

6. Encabezado multi-tenant

Cada comercio es un tenant identificado por un slug. En producción el slug sale del subdominio (local1.mostrador.io); en desarrollo local las solicitudes van a localhost y el slug se indica con el encabezado X-Tenant-Slug:

  • X-Tenant-Slug: {{tenantSlug}} en las rutas de un tenant (/me, /stores, /products, /public/..., /player/..., etc.).
  • X-Tenant-Slug: admin para el contexto de administración de la plataforma: allí solo responden /auth/*, /me y /tenants.
  • Un slug que no existe, está suspendido o tiene formato inválido responde 404 con code: "TENANT_NOT_FOUND".
  • Las rutas /auth/login y /auth/register no necesitan tenant.

Además del encabezado, el usuario debe ser miembro activo del tenant (si no, 403 NOT_A_MEMBER), salvo el root.

7. Orden de ejecución recomendado

La colección está numerada en el orden en que debe correr, de arriba hacia abajo. Las carpetas posteriores dependen de lo que crean las anteriores:

  1. 01 Admin: crea el tenant, el local y el dueño de la ejecución.
  2. 02 Auth y 03 Me: login, registro y sesión.
  3. 04 Stores, 05 Categories, 06 Products: datos del comercio. 06 deja un producto disponible.
  4. 07 Public y 08 Orders: usan el producto de 06 para crear y gestionar pedidos.
  5. 09 Media, 10 Content, 11 Screens: contenido y pantallas.
  6. 12 Player: usa la pantalla creada en 11.

8. Carpetas de la colección

En cada tabla, «Autenticación» indica la variable de token del encabezado Authorization y «Estado» el código HTTP que verifica la prueba de la solicitud.

9. Ejecutar toda la colección

9.1 Con el Collection Runner de Postman

  1. En la barra lateral, pasar el cursor sobre la colección «Mostrador API» y elegir Run (o menú de tres puntos y Run collection).
  2. Confirmar que el entorno seleccionado es «Mostrador local», con 1 iteración y sin retardo.
  3. Dejar todas las solicitudes marcadas y respetar el orden (no reordenar).
  4. Pulsar Run Mostrador API. Al terminar, Postman muestra el resumen con solicitudes, pruebas aprobadas y fallidas.

La ejecución completa tarda alrededor de 90 segundos.

9.2 Con la línea de comandos

Desde la carpeta backend/postman, con Postman CLI:

postman collection run Mostrador.postman_collection.json -e Mostrador-local.postman_environment.json

O con Newman (no requiere cuenta de Postman); --working-dir indica la carpeta contra la que se resuelven las rutas de los archivos de prueba:

npx -y newman@6 run Mostrador.postman_collection.json -e Mostrador-local.postman_environment.json --working-dir . --reporters cli,json --reporter-json-export postman-run.json

Postman CLI muestra la advertencia «No authorization data found» si no se inició sesión con postman login; la ejecución local funciona igual y solo se omite el envío del informe a la nube.

10. Cómo leer los resultados

  • Cada solicitud tiene una pestaña Test Results. Una prueba aprobada aparece como PASS y una fallida como FAIL, con el mensaje de la aserción (por ejemplo «expected response to have status code 200 but got 404»).
  • Todas las solicitudes verifican el código de estado («Responde 201», «Responde 404», etc.) y algunas verifican además campos de la respuesta («code SLUG_TAKEN», «Pedido generado»).
  • Las solicitudes de casos negativos (401, 403, 404, 409, 415, 422) se consideran aprobadas cuando el backend responde precisamente ese error.
  • En el resumen del Runner o de la consola, requests cuenta solicitudes ejecutadas y assertions las pruebas pm.test. El resultado esperado es cero fallidas.
  • La pestaña Console de Postman (View, Show Postman Console) muestra la solicitud y la respuesta crudas, útil para depurar.

12. Errores comunes y soluciones

SíntomaCausaSolución
401 UnauthorizedEl token falta o venció (dura 10 minutos). Ejemplo: {"message":"Unauthorized","statusCode":401}.Ejecutar de nuevo el login de la carpeta (o toda la colección desde el principio). Verificar que la solicitud tenga Authorization con la variable de token.
403 ForbiddenEl usuario no tiene el permiso o no es miembro del tenant. Ejemplo: code: "NOT_A_MEMBER" cuando el dueño llama a /tenants en el contexto admin.Usar el token del rol correcto (adminToken para /tenants) y el slug del tenant al que pertenece el usuario.
404 TENANT_NOT_FOUNDEl encabezado X-Tenant-Slug no corresponde a un tenant activo, o se pidió una ruta de tenant en el contexto admin.Revisar tenantSlug (se genera en cada ejecución) y que el tenant esté activo. Si se ejecuta una carpeta suelta, correr antes 01 Admin.
404 de otros recursosEl identificador no existe o es de otro tenant; el token de la pantalla es inexistente o la pantalla está desactivada.Verificar que las variables (storeId, productId, orderId, screenToken) no estén vacías; correr las carpetas anteriores.
409 ConflictDuplicado o estado inválido: email ya registrado, SLUG_TAKEN, CATEGORY_NAME_TAKEN, PRODUCTS_UNAVAILABLE, INVALID_STATUS_TRANSITION.Los 409 de la colección son casos negativos esperados. Si aparece uno inesperado (por ejemplo al registrar al dueño), limpiar las variables runId, tenantSlug y ownerEmail de la colección para generar valores nuevos.
415 / 422 en subidasFormato no soportado, video de más de 60 s, o duración enviada en un video.Usar los archivos de backend/http/samples. Son los códigos esperados en los casos negativos.
Upload path not found (archivo de prueba no encontrado)Postman o Newman no encuentran ../http/samples/promo.png porque el directorio de trabajo es otro.En Postman: Settings, General, Working directory = backend/postman, o volver a seleccionar el archivo en la solicitud. En Newman: agregar --working-dir con esa carpeta.
Backend caído (Could not get any response / ECONNREFUSED)El servidor no está levantado o escucha en otro puerto.Iniciar el backend con npm run start:dev en backend y comprobar que baseUrl del entorno sea http://localhost:3000.
Login del root falla (401) en 01 AdminLa base ya tiene un administrador raíz con otro email o contraseña.Reemplazar adminEmail y adminPassword del entorno por las credenciales del root existente.
Entorno sin seleccionarLas solicitudes quedan con {{baseUrl}} sin resolver.Elegir «Mostrador local» en el selector de entorno.
